# Project guide

## Current state

This is a Python prototype of **Find Before Build**, a coding harness with a reusable GitHub investigation skill. Search, scoring, model adapters, workspace tools, the CLI, a localhost browser UI, and paired evaluation are implemented. Aider 0.86.2 passed focused KoboldCpp edits; automatic engine selection uses it for one named file when installed and uses the native loop for larger tasks. A full Gemma 4 native run completed discovery, decision, file writes, and an independently passing behavior check. Qwen remains unverified. A courier price scraper was requested for dogfooding, but no working end-to-end courier scraper has been verified.

The current scope excludes image generation and image reading. [idea.md](idea.md) explains the product goal; [ARCHITECTURE.md](ARCHITECTURE.md) explains intended component contracts. This guide records what is actually implemented and where the prototype still differs from that intent.

## Architecture and technology choices

| Component | Implemented role | Why and tradeoff |
| --- | --- | --- |
| `harness.py` | CLI controller: creates a workspace, runs discovery and scoring, obtains a model decision, displays it, then enters a bounded coding tool loop and optionally writes JSON records | A small explicit controller is easy to inspect and demo. It supplies fewer features than a large agent framework. |
| `ui.py` | Local web form, live stage and repository shortlist panels, question/answer relay, activity log, output folder path, file preview, and automatic localhost app links | Makes the CLI usable without terminal interaction. It runs the same harness in a subprocess and stores each result under ignored `runs/ui-*`. Active jobs resume after a refresh. Completed jobs are available through View last build; a refresh starts from a clean request screen. On server restart, the latest completed record and output files are restored, but a previously active subprocess and its transient logs are not recovered. |
| `harness_core/clarify.py` and `CLARIFICATION_GUIDE.md` | Ask up to three material prebuild questions through the chosen model, with a small fallback if the model gives invalid output; native coding tools may ask later questions | Clarification happens before GitHub search so answers can affect the query and implementation. The model may still ask too much, too little, or an ambiguous question. |
| `find-before-build/SKILL.md` | Portable instructions for searching, scoring, and deciding before coding; the controller loads its body into the decision model prompt on discovery runs | Follows the Agent Skills file convention so it can be used outside this harness. The official reference validator accepted it. |
| `scripts/search_repos.py` | GitHub API queries, bounded candidate evidence, retrieval timestamps, and local cache | Structured metadata and URLs are more reproducible than ad hoc browsing. If a fresh search fails, it first uses an exact cache hit, then may use one recent cached search with strong query-term overlap, explicitly labelled `related_cache` and `cached_unverified`. It does not blend unrelated searches or claim the new queries ran. GitHub availability and rate limits remain dependencies. `GITHUB_TOKEN` is optional. |
| `scripts/score_repo.py` | Deterministic weighted score and flags | Makes the ranking inspectable. The fixed weights and README keyword fit are crude signals, so the model still assesses integration for the particular task. |
| `harness_core/reuse.py` | Shallow-clones up to three selected, permissively licensed, size-bounded shortlist repositories into ignored cache | Lets the model inspect real source rather than relying on README claims. Clone failures and license/size exclusions are reported. Cloned code is not run. |
| `harness_core/backends.py` | Normalizes text, tool calls, and usage from KoboldCpp and Gemini REST responses | The same controller can call a local model or Gemma 4. KoboldCpp reuses the user's GGUF runtime. Gemma requires a network request and API credential. |
| Aider | Existing coding engine selected automatically for one named file when installed; installation is isolated under `.cache/aider-venv` | Its edit application and Windows support save implementation time. Multi-file edits failed in one integrated run, so the native loop handles larger tasks by default. Aider is Apache-2.0 licensed. |
| `harness_core/workspace.py` | Allowlists workspace file/command tools plus read-only source inspection, attributed import tools, and bounded inspection of exact task-supplied HTTPS pages | Direct, auditable tools. Commands require terminal confirmation or can be disabled; approved commands are still able to affect more than the workspace, so approval matters. Imports copy license text and attribution. Page inspection does not follow redirects. |
| `eval.py` | Runs baseline (`--no-discovery`) and discovery arms in separate, identically seeded workspaces and runs task-defined acceptance commands afterward | Produces comparable observations without claiming general performance gains. It runs baseline first, so order and live API latency can affect results. |

The Gemini REST adapter also accepts an explicit Gemini model ID. Gemini 3/4 function calls require the model's opaque thought-signature parts to be returned unchanged with tool results; the adapter now retains those parts. This was added after a Gemini 3.8 Flash repair run returned HTTP 400 on its second tool call. A subsequent run passed multiple read-tool turns but repeated reads until `max_turns` without writing a file; Gemini coding reliability remains unverified. Gemma and Gemini outputs must be labelled by the model actually used.

Python 3.11+ standard library is the runtime dependency. This minimizes setup and avoids package compatibility issues on the observed Python 3.14.3 installation. Alternative HTTP/agent libraries could reduce adapter code but add installation, version, and hidden control-flow costs. The project license is MIT; this does not change third-party repository licenses.

For the Aider engine, Python 3.12 and `aider-chat` are installed in a separate environment rather than into the host's Python 3.14. Aider's local edit tests passed against KoboldCpp and independent Python assertions verified the results. A two-file integrated run returned exit code 0 after editing only one target; the controller now checks whether every planned file changed and labels this `partial_edit`. Aider is available with `--engine aider`, while `--engine auto` uses it only for a single explicitly named file when installed. A later one-file run created a working `greeting.py` in 10.55 seconds, using 831 reported tokens, with a passing assertion. This is a focused smoke result, not a reliability estimate.

## Actual request and data flow

1. A CLI invocation validates settings and resolves or creates the workspace. In the browser flow, `ui.py` creates a fresh workspace under ignored `runs/ui-*` and starts `harness.py` in a subprocess with the selected backend, native engine, clarification enabled, and model-requested shell commands disabled. The UI relays questions through a JSON line on standard output and an answer on standard input. Structured JSON progress events update the stage, candidate list, decision, and source-loading indicators without parsing the human-readable log. The browser polls the current job, shows generated files, and resumes an active job after refresh. A completed build stays available through View last build. Only one browser build runs at a time. The CLI waits until after the discovery decision is printed before preparing Aider's target files or taking a small-text-file snapshot for later change counting.
2. With `--clarify`, the chosen model proposes up to three questions based on the request and `CLARIFICATION_GUIDE.md`. The answers are appended to the task before discovery. The CLI uses terminal input; the browser shows each question as a form. The native coding loop can call `ask_user` later if a material detail remains unresolved. `--no-questions` disables these interactions for unattended evaluation.
3. Normal runs read `find-before-build/SKILL.md`, check its `name` metadata, ask the model to decompose the task into capabilities and two or three short GitHub queries, then call `search_repos.py`; a deterministic query fallback handles an invalid plan, and `--offline` allows exact cached evidence only. When a live search fails and there is no exact cache hit, one cached search from the last seven days may be used if at least two non-generic query terms overlap and the overlap covers at least 40% of the new terms. This is labelled as unverified cached evidence, not a successful fresh search. `score_repo.py` ranks the returned candidates. The skill's instructions are included in the model's decision prompt, while retrieval and scoring stay deterministic in scripts. The plan aims to search for both the requested product and reusable components; query quality still depends on the model and fallback rules.
4. The selected backend receives the task and scored evidence and returns a JSON reuse decision. The controller checks the action and candidate name, then prints the decision before any coding tool call. The current implementation falls back to a labelled `build_fresh` decision if discovery or model decision fails; it does **not** stop automatically. That means a network outage is visible but may still lead to new code without reuse evidence.
5. If the decision selects sources, the controller shallow-clones up to three shortlist repositories with verified permissive licenses and at most 50 MB reported repository size. It records clone warnings and commit IDs. The native model can list and read small source files and import a file into its workspace for adaptation. Import requires a license file, copies it, and writes `THIRD_PARTY_SOURCES.md`; source repositories remain in ignored cache and are never executed automatically. The model receives the task, decision, and top candidates. In default `--engine auto` mode, the controller chooses Aider for one explicitly named file when installed and the native loop otherwise; selected source inspection switches auto to native. Explicit `--engine aider` gets candidate summaries but no source inspection tools. Aider chooses up to eight editable filenames from the task. If none are named, it uses existing top-level files or defaults to `main.py` and `README.md` (`index.html` and `README.md` for a website request). It creates empty placeholders for missing targets and measures edits against that prepared state. The controller then writes a temporary prompt and runs Aider with those explicit files: `whole` edit format for one target, `diff` for multiple targets. The Aider prompt includes candidate names, scores, licenses, and flags but omits source URLs, which remain visible in the console and run record. It disables Aider's URL detection and Playwright so it does not fetch repository pages while editing; search remains the controlled GitHub API stage. It also disables Aider's Git integration, auto test/lint, shell suggestions, update check, and analytics, asks the model not to run commands, and redirects chat/input histories into the project's ignored `.cache/aider-history/` rather than the target workspace. Aider applies edits directly; this path does not use the native file-tool boundary or per-command confirmation. With `--engine native`, the model can request only the workspace and selected-source tools listed above. Native file paths are resolved against the workspace root, and a model-requested argv command uses `shell=False`, a 30-second timeout, and a terminal `y` confirmation. `--no-commands` denies native command requests.
6. The CLI prints the final status and, if `--record` is supplied, saves a JSON trace with discovery status, decision, tool log, changed files, time, model calls, and reported tokens. The change count reflects added text lines; it is not a quality measure. The UI reads the same record and displays its status and output files.

Repository READMEs, source files, user task text, and model tool arguments are inputs to validate, not authority to expand the allowlist. Discovery itself does not run candidate repositories; after a reuse decision, selected permissively licensed repositories can be cloned into ignored cache for read-only inspection, and imported files retain attribution. Command approval is interactive in the harness. The Gemini backend sends conversation content to Google's API; the KoboldCpp backend sends it to the configured local server. GitHub search sends queries to GitHub.

## Setup and use

Use Python 3.11 or newer; there are no Python packages to install for the native engine or UI. Start KoboldCpp separately with a chat-capable GGUF and its OpenAI-compatible endpoint. Hermes 3 8B was observed serving at `http://127.0.0.1:5001`. A Qwen 3.5 4B GGUF was present but untested; the harness cannot switch KoboldCpp's loaded model by changing `--model`, so load a different GGUF in the server first if you want to compare it.

From this directory:

```powershell
python harness.py "Build a CSV cleaner" --workspace .\demo-workspace --record .\runs\demo.json
```

For the browser UI, run `python ui.py` and open `http://127.0.0.1:8765/`. Enter a request, choose Gemini Flash (the default), Gemma 4, or local KoboldCpp, and answer questions in the page. The Gemini Flash choice uses the same Gemini API adapter with model `gemini-2.5-flash`; it is a distinct model and should be labelled as such in demos. The CLI also defaults to this Gemini model, while explicit backend/model flags retain the other options. The UI binds to `127.0.0.1`, checks its host and a session token, uses the native engine with `--clarify --no-commands`, and shows the current stage, GitHub shortlist with scores/licenses/flags, the reuse decision, activity log, and generated text-file previews. Green outlines mean the decision chose that repository; a Source loaded badge means the harness cloned it for inspection, not that generated code necessarily imported it. A build-fresh decision says explicitly that no repository was chosen. It holds one active build in memory; refreshing the page reconnects only while a job is active. View last build opens the latest completed job, including after a server restart, but no server restart can resume a still-running subprocess or its transient logs. CLI users can opt into the same prebuild questions with `--clarify`; without it, the native engine may still ask a question during coding. Model-requested commands require terminal confirmation in the CLI and are disabled in the UI.

The UI automatically serves a generated root or one-level-nested `index.html` on a separate loopback port as soon as it appears. After a successful build, it detects common generated server stacks: Flask (`app.py` or `main.py`), FastAPI (`app.py` or `main.py`), Vite, Next.js, and npm start scripts. It starts recognized services on available `127.0.0.1` ports and displays each link with startup status. For npm projects it runs `npm install --ignore-scripts` when `node_modules` is missing, then launches the app; this favors automatic preview while avoiding package lifecycle scripts. The frontend and backend may have separate links; their generated code must still connect them correctly, including any CORS settings. Runtime logs are saved beside the run record. Services stop when the UI server stops. This is a development convenience rather than a deployment or a general-purpose runner: other stacks, missing Python packages, invalid scripts, and apps that ignore `PORT` may not start. A reachable port means the server started, not that the generated app works end to end. The static preview uses a separate port so generated scripts do not share the UI's token origin.

Numbered `GEMINI_API_KEY_N` values can be stored in the ignored `.env`. Separate CLI processes can select keys by **name** with `--api-key-env GEMINI_API_KEY_1` and `--api-key-env GEMINI_API_KEY_2`, each with its own workspace. The values are not logged. This enables parallel runs but does not override provider quotas. If no name is supplied, the first available supported key is used.

Optional `GITHUB_TOKEN` increases GitHub API allowance. For Gemini (the CLI default), set `GEMINI_API_KEY` (or `GOOGLE_API_KEY`) and run `python harness.py "Build a CSV cleaner" --workspace .\gemini-demo --record .\runs\gemini.json`. For Gemma 4, add `--backend gemma-api`; for the local server, add `--backend koboldcpp`. The controller can read these credential names from this project's git-ignored `.env`; existing environment values take precedence. The selected backend defaults to `gemini-2.5-flash`, `gemma-4-26b-a4b-it`, or `koboldcpp` respectively, and `--model` overrides the choice. A full native-engine Gemma discovery-to-code run has succeeded; the Aider/Gemma combination remains untested. Do not commit credentials, private prompts, or sensitive run records.

The evaluation takes a JSON spec with `task`, `checks` (each an argv array), and optional `seed_files`. For example, `{"task":"Build a CSV cleaner","checks":[["python","-m","compileall","-q","."]]}`. Run `python eval.py task.json`; each arm's generated files and a `report.json` appear in a fresh `runs/eval-*` directory. The model cannot run commands during evaluation; the supplied checks run after each arm. `time_to_working_seconds` includes harness and check time when every acceptance check passes, and is `null` on failure. Aider model-call counts come from its `Tokens:` output lines, and its token counts may be rounded. Use an acceptance check that tests behavior, not compilation alone, for a meaningful result.

To install the optional Aider engine in this project folder with [uv](https://docs.astral.sh/uv/):

```powershell
uv venv .cache/aider-venv --python 3.12
uv pip install -r requirements-aider.txt --python .cache/aider-venv/Scripts/python.exe
```

The observed install used Aider 0.86.2, pinned in `requirements-aider.txt`. Its own [installation guide](https://aider.chat/docs/install.html) recommends an isolated Python 3.12 environment. `--engine auto` is the CLI default. Use `--engine native` or `--engine aider` to select one explicitly, or `--aider-path PATH` if Aider is installed elsewhere.

## Limitations and next checks

The model search plan and deterministic fallback can still miss synonyms or the right components. README keyword scoring can reward a relevant description without proving functionality; missing README/issue data under GitHub rate limits is marked unknown. A `build_fresh` fallback after a discovery failure keeps the run moving but weakens the find-before-build promise; the JSON record labels that case. Cloning and inspecting source does not prove it will combine successfully with another repository, and no complete courier integration has passed acceptance checks. Structural checks do not execute generated behavior or verify that a UI is playable. Native `run_command` confirmation occurs in a terminal and cannot sandbox an approved executable. The UI disables model-requested commands and cannot recover its in-memory job state after a restart. Aider's edit format and file selection affect whether small local models produce valid edits; both whole- and diff-format failures have been observed on different tasks. The filename heuristic only notices common extensions and top-level existing files, so it can omit a needed module or choose unsuitable defaults. Token counts depend on backend responses and Aider output parsing. The current snapshot covers small UTF-8 text files and does not count binary artifacts. One evaluation task cannot establish a general speedup or code-quality gain.

Next, test a task where reuse might be beneficial and test Qwen only after loading its GGUF in KoboldCpp. Keep failed Aider exploratory runs visible as limitations rather than folding them into the passing Gemma result.
