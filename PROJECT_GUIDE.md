# Project guide

## Current state

This is a Python prototype of **Find Before Build**, a coding harness with a reusable GitHub investigation skill. Search, scoring, model adapters, workspace tools, the CLI, and paired evaluation are implemented. Aider 0.86.2 passed focused KoboldCpp edits; automatic engine selection uses it for one named file when installed and uses the native loop for larger tasks. A full Gemma 4 native run completed discovery, decision, file writes, and an independently passing behavior check. Qwen remains unverified.

The current scope excludes image generation and image reading. [idea.md](idea.md) explains the product goal; [ARCHITECTURE.md](ARCHITECTURE.md) explains intended component contracts. This guide records what is actually implemented and where the prototype still differs from that intent.

## Architecture and technology choices

| Component | Implemented role | Why and tradeoff |
| --- | --- | --- |
| `harness.py` | CLI controller: creates a workspace, runs discovery and scoring, obtains a model decision, displays it, then enters a bounded coding tool loop and optionally writes JSON records | A small explicit controller is easy to inspect and demo. It supplies fewer features than a large agent framework. |
| `find-before-build/SKILL.md` | Portable instructions for searching, scoring, and deciding before coding; the controller loads its body into the decision model prompt on discovery runs | Follows the Agent Skills file convention so it can be used outside this harness. The official reference validator accepted it. |
| `scripts/search_repos.py` | GitHub API queries, bounded candidate evidence, retrieval timestamps, and local cache | Structured metadata and URLs are more reproducible than ad hoc browsing; GitHub availability and rate limits remain dependencies. `GITHUB_TOKEN` is optional. |
| `scripts/score_repo.py` | Deterministic weighted score and flags | Makes the ranking inspectable. The fixed weights and README keyword fit are crude signals, so the model still assesses integration for the particular task. |
| `harness_core/backends.py` | Normalizes text, tool calls, and usage from KoboldCpp and Gemini REST responses | The same controller can call a local model or Gemma 4. KoboldCpp reuses the user's GGUF runtime. Gemma requires a network request and API credential. |
| Aider | Existing coding engine selected automatically for one named file when installed; installation is isolated under `.cache/aider-venv` | Its edit application and Windows support save implementation time. Multi-file edits failed in one integrated run, so the native loop handles larger tasks by default. Aider is Apache-2.0 licensed. |
| `harness_core/workspace.py` | Allowlists `list_files`, `read_file`, `write_file`, and `run_command`; confines file paths to the selected workspace | Direct, auditable tools. Commands require terminal confirmation or can be disabled; approved commands are still able to affect more than the workspace, so approval matters. |
| `eval.py` | Runs baseline (`--no-discovery`) and discovery arms in separate, identically seeded workspaces and runs task-defined acceptance commands afterward | Produces comparable observations without claiming general performance gains. It runs baseline first, so order and live API latency can affect results. |

Python 3.11+ standard library is the runtime dependency. This minimizes setup and avoids package compatibility issues on the observed Python 3.14.3 installation. Alternative HTTP/agent libraries could reduce adapter code but add installation, version, and hidden control-flow costs. The project license is MIT; this does not change third-party repository licenses.

For the Aider engine, Python 3.12 and `aider-chat` are installed in a separate environment rather than into the host's Python 3.14. Aider's local edit tests passed against KoboldCpp and independent Python assertions verified the results. A two-file integrated run returned exit code 0 after editing only one target; the controller now checks whether every planned file changed and labels this `partial_edit`. Aider is available with `--engine aider`, while `--engine auto` uses it only for a single explicitly named file when installed. A later one-file run created a working `greeting.py` in 10.55 seconds, using 831 reported tokens, with a passing assertion. This is a focused smoke result, not a reliability estimate.

## Actual request and data flow

1. `harness.py` validates CLI settings and resolves or creates the chosen workspace. It waits until after the discovery decision is printed before preparing Aider's target files or taking a small-text-file snapshot for later change counting.
2. Normal runs read `find-before-build/SKILL.md`, check its `name` metadata, derive two queries from the task, and call `search_repos.py`; `--offline` allows cached evidence only. `score_repo.py` ranks the returned candidates. The skill's instructions are included in the model's decision prompt, while retrieval and scoring stay deterministic in scripts.
3. The selected backend receives the task and scored evidence and returns a JSON reuse decision. The controller checks the action and candidate name, then prints the decision before any coding tool call. The current implementation falls back to a labelled `build_fresh` decision if discovery or model decision fails; it does **not** stop automatically. That means a network outage is visible but may still lead to new code without reuse evidence.
4. The model receives the task, decision, and top candidates. In default `--engine auto` mode, the controller chooses Aider for one explicitly named file when installed and the native loop otherwise. Explicit `--engine aider` chooses up to eight editable filenames from the task. If none are named, it uses existing top-level files or defaults to `main.py` and `README.md` (`index.html` and `README.md` for a website request). It creates empty placeholders for missing targets and measures edits against that prepared state. The controller then writes a temporary prompt and runs Aider with those explicit files: `whole` edit format for one target, `diff` for multiple targets. The Aider prompt includes candidate names, scores, licenses, and flags but omits source URLs, which remain visible in the console and run record. It disables Aider's URL detection and Playwright so it does not fetch repository pages while editing; search remains the controlled GitHub API stage. It also disables Aider's Git integration, auto test/lint, shell suggestions, update check, and analytics, asks the model not to run commands, and redirects chat/input histories into the project's ignored `.cache/aider-history/` rather than the target workspace. Aider applies edits directly; this path does not use the native file-tool boundary or per-command confirmation. With `--engine native`, the model can request only the workspace tools listed above. Native file paths are resolved against the workspace root, and a model-requested argv command uses `shell=False`, a 30-second timeout, and a terminal `y` confirmation. `--no-commands` denies native command requests.
5. The CLI prints the final status and, if `--record` is supplied, saves a JSON trace with discovery status, decision, tool log, changed files, time, model calls, and reported tokens. The change count reflects added text lines; it is not a quality measure.

Repository READMEs, user task text, and model tool arguments are inputs to validate, not authority to expand the allowlist. Search never clones or runs candidate repositories. Command approval is interactive in the harness. The Gemini backend sends conversation content to Google's API; the KoboldCpp backend sends it to the configured local server. GitHub search sends queries to GitHub.

## Setup and use

Use Python 3.11 or newer; there are no Python packages to install. Start KoboldCpp separately with a chat-capable GGUF and its OpenAI-compatible endpoint. On this machine, `F:\koboldcpp.exe` was observed serving the Hermes 3 8B GGUF at `http://127.0.0.1:5001`. The Qwen 3.5 4B GGUF exists at `F:\Qwen\Qwen_Qwen3.5-4B-Q5_K_S.gguf`, but the harness cannot switch KoboldCpp's loaded model by changing `--model`; load that file in the server first if you want to compare it.

From this directory:

```powershell
python harness.py "Build a CSV cleaner" --workspace .\demo-workspace --record .\runs\demo.json
```

Optional `GITHUB_TOKEN` increases GitHub API allowance. For Gemma 4, set `GEMINI_API_KEY` (or `GOOGLE_API_KEY`) and run `python harness.py "Build a CSV cleaner" --workspace .\gemma-demo --backend gemma-api --record .\runs\gemma.json`. The controller can read those three credential names from this project's git-ignored `.env`; existing environment values take precedence. The adapter defaults to `gemma-4-26b-a4b-it`. A full native-engine discovery-to-code run has succeeded; the Aider/Gemma combination remains untested. Do not commit credentials, private prompts, or sensitive run records.

The evaluation takes a JSON spec with `task`, `checks` (each an argv array), and optional `seed_files`. For example, `{"task":"Build a CSV cleaner","checks":[["python","-m","compileall","-q","."]]}`. Run `python eval.py task.json`; each arm's generated files and a `report.json` appear in a fresh `runs/eval-*` directory. The model cannot run commands during evaluation; the supplied checks run after each arm. `time_to_working_seconds` includes harness and check time when every acceptance check passes, and is `null` on failure. Aider model-call counts come from its `Tokens:` output lines, and its token counts may be rounded. Use an acceptance check that tests behavior, not compilation alone, for a meaningful result.

To install the optional Aider engine in this project folder with [uv](https://docs.astral.sh/uv/):

```powershell
uv venv .cache/aider-venv --python 3.12
uv pip install -r requirements-aider.txt --python .cache/aider-venv/Scripts/python.exe
```

The observed install used Aider 0.86.2, pinned in `requirements-aider.txt`. Its own [installation guide](https://aider.chat/docs/install.html) recommends an isolated Python 3.12 environment. `--engine auto` is the CLI default. Use `--engine native` or `--engine aider` to select one explicitly, or `--aider-path PATH` if Aider is installed elsewhere.

## Meaningful changes and validation

- Replaced a documentation-only proposal with a standard-library Python prototype and an MIT license. The previous optional visual features were removed from scope at the user's request.
- Added a portable skill, timestamped GitHub retrieval and cache, deterministic scoring, two backend adapters, workspace-confined file tools, and a staged CLI. The official `skills-ref` validator accepted `find-before-build`. A live GitHub search returned three candidates, and the scoring script ranked them.
- A local Hermes end-to-end smoke task created `hello.py` and `README.md` after the harness retried a prose-only answer: three model calls, 24.09 seconds, and 2,231 reported tokens. An earlier run without the retry produced no files. This is evidence for one small task, not a general coding success rate.
- Installed Aider 0.86.2 in an isolated Python 3.12 environment. A separate Aider-to-KoboldCpp smoke edit passed a Python assertion. The controller now delegates editing to Aider after displaying the decision.
- An integrated Aider run reached the editing stage, but two-file `whole` format produced a stray filename from nested README formatting. Explicit-file `diff` setup passed focused smoke runs, yet another integrated two-file run changed only one file while exiting 0. The controller now reports `partial_edit` for such cases and auto mode uses the native engine for multi-file tasks. One-file Aider `greeting.py` creation passed an independent assertion. Early CSV evaluations failed acceptance in both arms; neither shows a discovery benefit.
- An exploratory discovery run passed repository URLs into Aider's editing prompt. Aider attempted URL detection and optional Playwright setup, taking 144 seconds and writing no files. The wrapper now omits URLs from the Aider prompt and disables URL detection and Playwright. Source URLs remain available in the visible discovery evidence and JSON record.
- Sixteen standard-library unit tests pass; one Windows symlink test is skipped because that operation is unavailable in the test environment (17 total). The added regression checks cover truthful Aider partial-edit status and query terms.
- Added a paired evaluation runner that creates separate seeded workspaces and runs the same checks for both arms. The first passing run is recorded below; it shows overhead, so no improvement is claimed.
- A live Gemma 4 API run with the native engine, discovery enabled, `--no-commands`, and `--max-turns 8` searched and scored repositories, displayed `build_fresh` before code, wrote `calculator.py` and `README.md`, and ended `finished` with exit 0. The run took 29.23 seconds, used four model calls and 4,411 reported tokens, and added 16 lines. An independent assertion `add(2, 3) == 5` passed. The ignored record is `runs/gemma-full.json`. One candidate was flagged stale and two had unknown license in the displayed shortlist; that run began before the later explicit license-field addition to candidate records.
- A paired Gemma 4/native evaluation on 17 October 2026 used the same calculator task, model, seed state, and behavior/README checks in two separate workspaces. Both arms passed. Without discovery: 11.410 seconds to working result, 1,965 reported API tokens, two changed files, 15 added lines. With discovery: 28.618 seconds, 4,390 reported API tokens, two changed files, 13 added lines. The discovery arm searched five live candidates and chose `build_fresh` because the function was too small to justify reuse. The shareable, path-free result is [results/gemma-calculator-summary.json](results/gemma-calculator-summary.json), based on [examples/calculator.eval.json](examples/calculator.eval.json); the detailed report remains ignored at `runs/eval-20261017T132317Z/report.json`. This demonstrates overhead and no acceptance gain on this task; it does not establish general speed or quality effects.
- Qwen loading remains pending unless subsequent recorded validation is added here.

## Limitations and next checks

The initial query generator is deterministic and can miss synonyms, although it now includes content terms in the query. README keyword scoring can reward a relevant description without proving functionality. A `build_fresh` fallback after a discovery failure keeps the run moving but weakens the find-before-build promise; the JSON record labels that case. Native `run_command` confirmation occurs in a terminal and cannot sandbox an approved executable. Aider's edit format and file selection affect whether small local models produce valid edits; both whole- and diff-format failures have been observed on different tasks. The filename heuristic only notices common extensions and top-level existing files, so it can omit a needed module or choose unsuitable defaults. Token counts depend on backend responses and Aider output parsing. The current snapshot covers small UTF-8 text files and does not count binary artifacts. One evaluation task cannot establish a general speedup or code-quality gain.

Next, test a task where reuse might be beneficial and test Qwen only after loading its GGUF in KoboldCpp. Keep failed Aider exploratory runs visible as limitations rather than folding them into the passing Gemma result.
