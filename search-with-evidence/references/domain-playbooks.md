# Domain-specific inspection

Use these as starting points, not universal score weights. Criteria come from the user's decision.

## GitHub and software

Resolve whether the user wants a hosting platform, a repository, a library, or an implementation approach. Search the function and its specialist components. GitHub defaults to name/description/topics; add `in:readme` when those fields miss relevant behavior. Use `language:` and `topic:` deliberately rather than filtering away every possible integration approach.

Inspect the actual API/source entry point, package manifest, examples/tests, license, releases, and issue context. Follow upstream/maintained successor/dependency links. Resource lists can identify candidates but are not implementations. Stars and last-push dates alone cannot establish usability. For a combination, state the input/output boundary between components and the work needed to connect them. Source inspection is not an execution result.

## Courses and teaching sites

Translate "best course" into the learner's intended outcome, current level, prerequisites, learning format, language, time, practical work, cost/access, and need for a recognized certificate. Do not confuse course depth with suitability for beginners.

Find the official syllabus and prerequisites, inspect a sample lesson or assignment if accessible, and verify current enrollment and cost on the provider's own pages. Separate free learning access, a free trial, auditing, and a paid certificate. Use independent learner reports for experience and limitations, not to override objective syllabus/access facts. Don't treat affiliate roundups, view counts, or a prestigious provider as evidence of pedagogical fit. Unknown completion/support quality stays unknown.

## Research papers

Define the research question, target setting, methods, datasets/population, outcome, and whether seminal work or recent progress is needed. Search synonyms across available scholarly sources; record which indexes were actually searched. Follow both backward references and forward citations, when the host can obtain them. The most-cited paper may establish a baseline while a less-cited one addresses the user's exact setting.

Verify bibliographic identity and versions. Read methods, experimental setup, comparisons, limitations, and relevant results rather than trusting abstracts alone. Separate preprints from peer-reviewed publications; check corrections/retractions when material. Record when code/data is merely linked versus independently checked. Do not claim a paper's benchmark improvement transfers to our skill without evaluating that transfer. A systematic review requires its own explicit search/screening protocol.

## Connected databases and private collections

Use the available authorized connector or read-only client. Inspect schema, field definitions, identifiers, date ranges, and access scope before choosing filters. Combine structured constraints with full-text or semantic search only when the backend supports them. Parameterize user values; do not guess tables or run writes, migrations, or unrestricted exports. Sampling is useful for understanding vocabulary but cannot establish that no matching record exists.

Keep public and private provenance distinct. An internal document cannot be used as a public citation, and private text should not be pasted into public search queries. State access/coverage gaps rather than looking for ways around them.
